# \(202311\.N\) How to configure and use GNMI \(Telemetry\) \(Updated\)



# How to Configure Telemetry

## Configuration for Telemetry (dial-in mode)

The configuration of Telemetry can be done either by editing /etc/sonic/config\_db.json and reloading the configuration.

- Configuration structure can be editted in **/etc/sonic/config\_db.json**.

```
    {
        "GNMI": {
            "certs": {
                "ca_crt": "/path/to/ca_crt",
                "server_crt": "/path/to/server_crt",
                "server_key": "/path/to/server_key"
            },
            "gnmi": {
                "client_auth": "<boolean>",
                "log_level": "<level number>",
                "port": "<port number>"
            }
        }
    }
```

    
- Because **/etc/sonic** will be mounted into the container at the same location, it is recommended to place **ca\_crt**, **server\_crt**, and **server\_key** in the **/etc/sonic/telemetry** directory on the host.
- If **server\_crt** and **server\_key **are left blank, the telemetry will enter insecure mode. If the entire **certs** section is not configured, Telemetry will enter noTLS mode.
- If **client\_auth **is set to **false** or empty (e.g., ""), when value is empty, it allows clients to connect to Telemetry server without certificate.
- These parameters of Telemetry are passed during startup, so after configuring them, it's necessary to reload config to restart the telemetry service.

```bash
sudo config reload -y
```

    
- If the above settings are configured, you will see that the Telemetry process is executed with the following parameters inside the Telemetry container:

```bash
/usr/sbin/telemetry -logtostderr --server_crt /path/to/server_crt --server_key /path/to/server_key --ca_crt /path/to/ca_crt --port 8080 --allow_no_client_auth -v=2
```

    
- Example configuration for enable inseucure mode for testing:

In insecure mode, an unverified certificate is generated, so the transmission is still encrypted.

    

```
{
	"GNMI": { 
		"certs": { 
			"ca_crt": "", 
			"server_crt": "", 
			"server_key": "" 
		}, 
		"gnmi": { 
			"client_auth": "false", 
			"log_level": "2", 
			"port": "8080" 
		} 
	} 
}
```

    
- Example configuration for enable inseucure mode with vrf (mgmt) for testing:

    

```
{
	"GNMI": { 
		"certs": { 
			"ca_crt": "", 
			"server_crt": "", 
			"server_key": "" 
		}, 
		"gnmi": { 
			"client_auth": "false", 
			"log_level": "2", 
			"port": "8080",
            "vrf": "mgmt" 
		} 
	} 
}
```

    

## Configuration for Dial-out

Dial-out settings are dynamically read from the Redis database, so if you want to configure dial-out, you will need to directly configure it in the Redis database.

- Configuration structure can be editted in** /etc/sonic/config\_db.json**.

```js
  {
      "TELEMETRY_CLIENT": {
          "Global": {
              "encoding": "JSON_IETF",
              "retry_interval": "30",
              "src_ip": "<the IP of this machine>",
              "unidirectional": "true"
          },
          "DestinationGroup_<Group Name>": {
              "dst_addr": "<the IP of collector>,..."
          },
          "Subscription_<Subscription Name>": {
              "dst_group": "<Group Name>",
              "path_target": "<Target DB>",
              "paths": "<Path>,...",
              "report_interval": "<interval ms>",
              "report_type": "<report type>"
          }
      }
  }
```

    

# How to Use Telemetry

After Edgecore SONiC 202211.2.1, due to the write flag being enabled by default, password and jwt-based user authentication are activated. When using the gNMI tool, you must include a username and password.

Telemetry can read or configure network settings, which can be achieved using gNMI tools. Below are some tools and examples:

## Clients for Telemetry

- **gnmi\_get**: \[[https://github.com/jipanyang/gnxi/tree/master/gnmi\_get](https://github.com/jipanyang/gnxi/tree/master/gnmi_get)\]

This tool allows for retrieval of one or more paths.
    - Example: get **MTU **of **Ethernet0**

```bash
./gnmi_get -insecure -xpath /openconfig-interfaces:interfaces/interface[name=Ethernet0]/config/mtu -target_addr localhost:8080 -xpath_target OC-YANG -username admin -password 123456
```

        
- **gnmi\_set**: \[[https://github.com/google/gnxi/tree/master/gnmi\_set](https://github.com/google/gnxi/tree/master/gnmi_set)\]

> This tool allows for update, replace and delete operations.
    - Example: get **MTU **of **Ethernet0**

```bash
./gnmi_set -insecure -update /openconfig-interfaces:interfaces/interface[name=Ethernet0]/config/mtu:@./mtu.json -target_addr localhost:8080 -xpath_target OC-YANG -username admin -password 123456
```

        
- **gnmi\_cli**: \[[https://github.com/jipanyang/gnmi/tree/master/cmd/gnmi\_cli](https://github.com/jipanyang/gnmi/tree/master/cmd/gnmi_cli)\]

> This tool allows for dial-in Subscription operations as well as Capabilities request to list available models.

### Parameters in the above client.

- common
    - **target\_addr**: The target address in the format of host:port.
    - **xpath\_target**: The xpath\_target in the parameters of the above program, refers to the specific target being accessed, categorized into DB, non-DB, or OC-YANG (OpenConfig YANG).
        - DB: refers to the names of various databases within the Redis database.
            - APPL\_DB
            - ASIC\_DB
            - COUNTERS\_DB
            - LOGLEVEL\_DB
            - CONFIG\_DB
            - FLEX\_COUNTER\_DB
            - STATE\_DB
        - non-DB: refers to data that is not stored within a specific database.
            - OTHERS, refer to Appendix 1: Paths and Examples for Target OTHERS
        - OC-YANG: refers to URLs represented using the OpenConfig YANG format.
            - OC-YANG
    - **xpath**: In order to access network settings, a specific URL is required, which can be in either openconfig-yang or sonic-yang format.
        - sonic-yang format  
The URL in sonic-yang format corresponds to the structure inside the Redis database. For example, the **"TELEMETRY|certs ca\_crt"** would be represented as **"TELEMETRY/certs/ca\_crt"**.
        - openconfig yang format  
The URL in OpenConfig YANG format can reference the REST API URL.
    - **insecure**: Skip TLS validation.
    - **cert**: Certificate file.
    - **key**: Private key file.
    - **ca**: CA certificate file. Used to verify server TLS certificate.
- gnmi\_set
    - **update**: **xpath:value** pair to be updated. Value can be numeric, boolean, string, or IETF JSON file (. starts with '@').
    - **replace**: **xpath:value** pair to be replaced. Value can be numeric, boolean, string, or IETF JSON file (. starts with '@').
    - **delete**: **xpath** to be deleted.

## User Authentication

The gNMI service supports 3 types of user authentication: **password**, **JWT**, and **cert**. However, they cannot be configured through CONFIG\_DB now.
In the current default settings, password and JWT authentication are enabled, while cert-based authentication is not activated.

- For password authentication: 
    - You need to include the username and password parameters during get/set operations. 
    - The server will then use this account information to authenticate by connecting to the host via SSH.
- For JWT authentication:
    - 

You need to use `gNOI` to obtain the JWT token.

Example:

```
./gnoi_client -module Sonic -rpc authenticate -insecure -target localhost:8080 -jsonin '{"username": "admin", "password": "123456"}'

Sonic Authenticate
{"Token":{"access_token":"eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6ImFkbWluIiwicm9sZXMiOlsiYWRtaW4iXSwiZXhwIjoxNzI1MDA2MjcyfQ.bQsRVWNwFVxCjSnXMj6pdEsWHw8cfmVOgw5yRqr9FDw","type":"Bearer","expires_in":3600}}
```

  

    - And then you can then use this token to perform operations.

```
./gnmi_get -insecure -xpath "/openconfig-interfaces:interfaces/interface[name=Ethernet0]/config/mtu" -target_addr localhost:50051 -xpath_target OC-YANG -jwt_token "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6ImFkbWluIiwicm9sZXMiOlsiYWRtaW4iXSwiZXhwIjoxNzI1MDA2MjcyfQ.bQsRVWNwFVxCjSnXMj6pdEsWHw8cfmVOgw5yRqr9FDw"
```

        
- For cert-based authentication:
    -  It works by using the common name from the certificate as the username, which is then looked up within the Telemetry container for authentication.

# Appendix 1: Paths and Examples for Target OTHERS

Below is a detailed table of available paths in the system along with their descriptions.

| Path | **Description** |
| --- | --- |
| `/platform/cpu` | Retrieves the current CPU utilization. |
| `/proc/uptime` | Retrieves the system's total uptime. |
| `/proc/meminfo` | Provides detailed memory usage information. |
| `/proc/diskstats` | Provides statistics on disk I/O operations. |
| `/proc/loadavg` | Retrieves the system's current load average. |
| `/proc/vmstat` | Provides the status of virtual memory. |
| `/osversion/build` | Retrieves the OS build version information. |

## Examples

Here is an example command to retrieve information from a specific path:

```
./gnmi_get -insecure -xpath /proc/uptime -target_addr localhost:8080 -xpath_target OTHERS
```

Replace the `-xpath` value with the desired path to retrieve data from other endpoints.
